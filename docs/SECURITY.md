# Модель безопасности и защита данных в GameTracker

Руководство по модели угроз, изоляции учётных данных, защите от атак и обеспечению приватности в экосистеме GameTracker.

---

## 1. Модель угроз и границы доверия (Threat Model)

В проекте определены три изолированные зоны доверия:

```
[ Недоверенная зона ]            [ Доверенная зона ]           [ Внешняя доверенная зона ]
  Android Client                 Ktor BFF Gateway                     Twitch / IGDB
 (Реверс-инжиниринг APK)      (Секреты, Rate Limiter, Кэш)        (OAuth2 Identity & API)
        |                                  |                                     |
        |--- HTTP (Без секретов) --------->|                                     |
        |                                  |--- POST /oauth2/token (Secrets) --->|
        |                                  |<-- Access Token --------------------|
        |                                  |--- POST /v4/games (APICalypse) ---->|
        |<-- Санитизированный JSON --------|<-- Сырой JSON ----------------------|
```

1. **Мобильное приложение (Android APK)** — считается потенциально скомпрометированной средой. Декомпиляция APK с помощью инструментов вроде `jadx` или `apktool` позволяет атакующему извлечь любые статические строки, ключи и встроенные конфигурации.
2. **Ktor BFF Gateway (`:backend`)** — защищённый серверный периметр. Хранит чувствительные конфигурации, изолирует OAuth2-секреты от внешнего мира и контролирует входящий поток запросов.
3. **Upstream IGDB API** — внешняя сторона, предоставляющая данные по строгому протоколу OAuth2 Client Credentials с жёстким лимитом квот (4 запроса в секунду).

## 2. Изоляция секретов и жизненный цикл токенов OAuth2

- **Отсутствие секретов в клиенте**: Исходный код приложения `:app`, манифесты и ресурсы не содержат ни `Client-ID`, ни `Client-Secret`.
- **Серверный обмен токенов**: BFF отправляет форму `application/x-www-form-urlencoded` напрямую на авторизационный сервер Twitch (`https://id.twitch.tv/oauth2/token`).
- **CAS-ротация токенов в памяти**:
  - Токен хранится исключительно в оперативной памяти сервера с использованием потокобезопасного механизма (`AtomicReference` / `Mutex`).
  - При одновременном обращении нескольких корутин за истекшим токеном выполняется атомарная операция проверки и замены (Compare-And-Swap), предотвращающая параллельные запросы на выпуск дублирующих токенов.
- **Автоматическая инвалидация**:
  - При возникновении ошибки HTTP 401 Unauthorized от IGDB кэшированный токен немедленно сбрасывается, и сервис автоматически производит повторную авторизацию.

## 3. Защита квот и предотвращение атак типа "Отказ в обслуживании" (DoS)

API IGDB накладывает жёсткую квоту — **не более 4 запросов в секунду** на аккаунт. Превышение квоты приводит к моментальной блокировке (HTTP 429 Too Many Requests).

### Монотонный `SmoothRateLimiter`
В сервисе `:backend` реализован кастомный планировщик очереди `SmoothRateLimiter`:
- Минимальный монотонный интервал между upstream-запросами составляет **300 мс** ($\le 3.33\text{ req/s}$).
- Это исключает всплески нагрузки на стыках секундных интервалов (в отличие от стандартного алгоритма «корзины токенов»).

### Single-Flight кэширование (Caffeine + CompletableDeferred)
Для предотвращения эффекта «собачьей своры» (cache stampede / dogpiling), когда сотни клиентов одновременно запрашивают один и тот же популярный поисковый запрос:
- Запрос заворачивается в изолированный `SupervisorScope`.
- Параллельные вызовы ожидают один и тот же экземпляр `CompletableDeferred`.
- Отмена клиентского HTTP-запроса не отменяет уже начатый upstream-запрос к IGDB, гарантируя наполнение кэша и сохранение актуальности данных.

## 4. Защита от инъекций запросов (APICalypse Sanitization)

IGDB использует собственный язык запросов **APICalypse** (синтаксис вида `fields name, rating; search "query"; limit 20;`). Прямая конкатенация пользовательской строки в тело запроса открывает уязвимость инъекции параметров (например, инъекция `; fields *;` или подмена лимитов).

Модуль `SearchQueryValidator` выполняет строгую фильтрацию входящих параметров:
1. **Нормализация Unicode**: Приведение строки к канонической форме **NFC** для исключения атак с использованием визуально схожих символов (гомоглифов).
2. **Ограничение длины**: Строго от 1 до 100 символов.
3. **Белый список символов (Allowlist)**: Разрешены только буквы алфавитов, цифры, пробелы и безопасная пунктуация. Служебные символы APICalypse (точка с запятой `;`, фигурные скобки `{}`, кавычки `"`) экранируются или отклоняются с кодом HTTP 400 Bad Request.

## 5. Безопасность Ingress и защита от спуфинга IP-адресов

При развёртывании сервиса за обратным прокси-сервером (Reverse Proxy, Cloudflare, Nginx):
- Сервер анализирует непосредственный сокетный адрес клиента (`local.remoteHost`).
- Заголовок `X-Forwarded-For` обрабатывается **только в том случае**, если непосредственный TCP-пир входит в доверенный список `trustedHosts`.
- Если запрос пришёл от неавторизованного узла, заголовок `X-Forwarded-For` отбрасывается, предотвращая спуфинг клиентских IP-адресов для обхода клиентского rate limiting.

## 6. Приватность пользователей и гигиена логов

- **Локальное хранение данных библиотеки**: Оценки, заметки, статусы прохождения игр и сыгранные часы хранятся **строго локально на устройстве в Room SQLite**. Они никогда не передаются на сервер BFF или сторонние сервисы аналитики.
- **Маскирование логов**: Сетевые интерцепторы и логгеры Ktor санитизируют чувствительные заголовки (`Authorization`, токены) и не логируют полные персональные параметры.
- **Унификация ошибок**: Внутренние исключения бэкенда (стектрейсы, сбои базы данных или сетевые таймауты) никогда не отдаются наружу клиенту. Публичный контракт возвращает унифицированный безопасный объект `ErrorResponse`.

# Модель безопасности и защита данных в GameTracker

Руководство по модели угроз, изоляции учётных данных, защите от атак и обеспечению приватности в экосистеме GameTracker.

---

## 1. Модель угроз и границы доверия (Threat Model)

В проекте определены три изолированные зоны доверия:

```
[ Недоверенная зона ]            [ Доверенная зона ]           [ Внешняя доверенная зона ]
  Android Client                 Ktor BFF Gateway                     Twitch / IGDB
 (Реверс-инжиниринг APK)      (Секреты, Rate Limiter, Кэш)        (OAuth2 Identity & API)
        |                                  |                                     |
        |--- HTTP (Без секретов) --------->|                                     |
        |                                  |--- POST /oauth2/token (Secrets) --->|
        |                                  |<-- Access Token --------------------|
        |                                  |--- POST /v4/games (APICalypse) ---->|
        |<-- Санитизированный JSON --------|<-- Сырой JSON ----------------------|
```

1. **Мобильное приложение (Android APK)** — считается потенциально скомпрометированной средой. Декомпиляция APK с помощью инструментов вроде `jadx` или `apktool` позволяет атакующему извлечь любые статические строки, ключи и встроенные конфигурации.
2. **Ktor BFF Gateway (`:backend`)** — защищённый серверный периметр. Хранит чувствительные конфигурации, изолирует OAuth2-секреты от внешнего мира и контролирует входящий поток запросов.
3. **Upstream IGDB API** — внешняя сторона, предоставляющая данные по строгому протоколу OAuth2 Client Credentials с жёстким лимитом квот (4 запроса в секунду).

## 2. Изоляция секретов и жизненный цикл токенов OAuth2

- **Отсутствие секретов в клиенте**: Исходный код приложения `:app`, манифесты и ресурсы не содержат ни `Client-ID`, ни `Client-Secret`.
- **Серверный обмен токенов**: BFF отправляет форму `application/x-www-form-urlencoded` напрямую на авторизационный сервер Twitch (`https://id.twitch.tv/oauth2/token`).
- **Жизненный цикл токенов в памяти**:
  - Быстрый путь (fast path) чтения активного токена через неблокирующий `AtomicReference.get()`.
  - При истечении срока действия токена вход в критическую секцию сериализуется через `Mutex.withLock` с повторной проверкой (double-check), гарантируя ровно один сетевой запрос на получение свежего токена.
  - Условная инвалидация (compare-aware invalidation): при возникновении HTTP 401 Unauthorized сброс токена выполняется через `tokenState.updateAndGet`, исключая сброс нового токена, если параллельная корутина уже успела его обновить.

## 3. Защита квот и предотвращение атак типа "Отказ в обслуживании" (DoS)

API IGDB накладывает жёсткую квоту — **не более 4 запросов в секунду** на аккаунт. Превышение квоты приводит к моментальной блокировке (HTTP 429 Too Many Requests).

### Монотонный `SmoothRateLimiter`
В сервисе `:backend` реализован кастомный планировщик очереди `SmoothRateLimiter`:
- Минимальный монотонный интервал между upstream-запросами составляет **300 мс** ($\le 3.33\text{ req/s}$).
- Это исключает всплески нагрузки на стыках секундных интервалов (в отличие от стандартного алгоритма «корзины токенов»).

### Single-Flight кэширование (Caffeine + SupervisorJob)
Для предотвращения эффекта «собачьей своры» (cache stampede / dogpiling), когда несколько клиентов одновременно запрашивают один и тот же ещё не закэшированный ключ:
- Вычисление выполняется в `CoroutineScope` уровня приложения на базе `SupervisorJob() + Dispatchers.Default`.
- Все параллельные запросы с одинаковым ключом ожидают единого вычисления (single-flight).
- Отмена одного клиентского HTTP-запроса не отменяет вычисление для других подписчиков и не прерывает прогрев кэша Caffeine.
- При сбое upstream-запроса ожидающая запись атомарно удаляется, не отравляя кэш ошибкой.

## 4. Защита от инъекций запросов (APICalypse Sanitization)

IGDB использует собственный язык запросов **APICalypse** (синтаксис вида `fields name, rating; search "query"; limit 20;`). Прямая конкатенация пользовательской строки в тело запроса открывает уязвимость инъекции параметров (например, инъекция `; fields *;` или подмена лимитов).

Модуль `SearchQueryValidator` выполняет строгую фильтрацию входящих параметров:
1. **Нормализация Unicode NFC**: Приведение строки к канонической форме **NFC** для стабильного представления символов и формирования детерминированных ключей кэша. *(Важно: NFC обеспечивает каноническое представление эквивалентных последовательностей, но не выполняет детекцию гомоглифов или визуально схожих символов разных алфавитов).*
2. **Ограничение длины**: Строго от 1 до 100 символов (code points), пустые и состоящие только из пробелов/невидимых символов строки отклоняются с ошибкой HTTP 400 Bad Request.
3. **Политика валидации**: Разрешён широкий диапазон Unicode-текста, включая буквы национальных алфавитов, цифры, пунктуацию и эмодзи. Отклоняются:
   - Управляющие символы ISO (`Character.isISOControl`);
   - Двойные кавычки `"` и обратный слэш `\` (разделители строковых литералов APICalypse);
   - Невидимые символы форматирования и двунаправленного текста (кроме Zero-Width Joiner в контексте эмодзи).

## 5. Безопасность Ingress и защита от спуфинга IP-адресов

При развёртывании сервиса за обратным прокси-сервером (Reverse Proxy, Cloudflare, Nginx):
- Сервер анализирует непосредственный сокетный адрес клиента (`local.remoteHost`).
- Заголовок `X-Forwarded-For` обрабатывается **только в том случае**, если непосредственный TCP-пир входит в доверенный список `trustedHosts`.
- Если запрос пришёл от неавторизованного узла, заголовок `X-Forwarded-For` отбрасывается, предотвращая спуфинг клиентских IP-адресов для обхода клиентского rate limiting.

## 6. Приватность пользователей и гигиена логов

- **Локальное хранение данных библиотеки**: Оценки, заметки, статусы прохождения игр и сыгранные часы хранятся в Room SQLite на устройстве. Они **не отправляются на BFF как raw fields и не уходят в аналитику**. При `allowBackup=true` база `gametracker.db` может участвовать в облачном резервном копировании Android и в device transfer — это не синхронизация аккаунта GameTracker, а транспорт ОС.
- **Рекомендации**: ranking выполняется на устройстве. В `live` запрос кандидатов передаёт до 50 идентификаторов игр библиотеки как `exclude`, до 10 seed IDs как `similarTo` и derived-теги предпочтений. Оценки, статусы, заметки и часы как raw fields не передаются, но по идентификаторам BFF может увидеть часть или весь состав небольшой библиотеки. Это не analytics upload, однако запрос содержит пользовательские preference signals.
- **Уведомления о релизе**: best-effort и только для игр, где пользователь явно включил переключатель (WorkManager + дедуп по `eventKey`, включающему игру, тип события и релевантные даты). Это не at-least-once: переход даты может быть потерян, если его не записали до остановки процесса.
- **Маскирование логов**: Сетевые интерцепторы и логгеры Ktor санитизируют чувствительные заголовки (`Authorization`, токены). Обработчик ошибок логирует только path запроса, без query string; поисковые маршруты пишут `queryLength` и наличие фильтров, а не полный `q`.
- **Унификация ошибок**: Внутренние исключения бэкенда (стектрейсы, сбои базы данных или сетевые таймауты) никогда не отдаются наружу клиенту. Публичный контракт возвращает унифицированный безопасный объект `ErrorResponse`.

---

## 7. Граница развёртывания BFF

Текущий BFF рассчитан на **локальный / однопользовательский demo**, а не на публичный интернет-сервис. Per-IP rate limit и in-memory cache защищают квоту IGDB на одном инстансе, но **клиентской аутентификации нет**: любой, кто достучится до порта, сможет расходовать upstream quota.

Для публичного deployment отдельно потребуются как минимум: TLS termination, authentication или app attestation по выбранной модели, edge rate limiting, secret manager, metrics/alerting и shared/distributed rate limiting при нескольких инстансах. Пока этого нет, публичный BFF URL намеренно не публикуется.
